La métaphore : le distributeur de billets

Tu n'as jamais ouvert un DAB pour prendre du cash. Tu utilises son interface.

Ce que tu vois (public)

J1.25
Sans encapsulation : champ libre

Tout est public. N'importe quel code peut écrire n'importe quelle valeur, à n'importe quel moment.

La classe

class Film
{
    public string Titre;
    public int Annee;
    public string Genre;
}

Le code qui l'utilise

var film = new Film();
film.Titre = "Inception";
film.Annee = -3000;        // Aucun problème
film.Genre = null;          // Aucun problème
film.Annee = 99999;         // Aucun problème
film.Titre = "";            // Aucun problème
Aucune règle métier protégée. Le bug arrivera dans 6 mois, dans une autre partie du code, et tu ne sauras pas qui a corrompu l'objet.
J1.26
Avec encapsulation : champs privés + propriétés

Les champs deviennent private. L'accès passe par des propriétés public que tu contrôles.

La classe encapsulée

class Film
{
    private string _titre;
    private int _annee;

    public string Titre
    {
        get { return _titre; }
        set { _titre = value; }
    }

    public int Annee
    {
        get { return _annee; }
        set { _annee = value; }
    }
}

Côté utilisateur

var film = new Film();
film.Titre = "Inception";  // Passe par le set
var t = film.Titre;         // Passe par le get
L'utilisateur ne voit aucune différence d'API. Mais tu peux désormais valider, logger, transformer dans le get / set sans changer une ligne chez lui.
J1.27
Anatomie d'une propriété C#

Trois formes selon le besoin, du plus court au plus contrôlé.

1. Auto-property

public string Titre
    { get; set; }

Le compilateur génère le champ caché. Défaut moderne tant qu'il n'y a pas de validation.

2. Avec backing field

private int _annee;
public int Annee
{
    get => _annee;
    set => _annee = value;
}

Champ explicite. Indispensable dès qu'on veut valider ou transformer.

3. Propriété calculée

public int Age =>
    DateTime.Now.Year
    - Annee;

Pas de stockage. Recalculée à chaque lecture, toujours à jour.

Tu commences en auto-property. Tu passes en full property dès qu'une règle métier doit vivre dans le setter.
J1.28
Le setter, ton garde du corps

La vraie valeur de l'encapsulation : impossible de poser un état invalide sur l'objet.

Validation dans le setter

private int _annee;

public int Annee
{
    get => _annee;
    set
    {
        if (value < 1888 ||
            value > DateTime.Now.Year + 5)
            throw new ArgumentException(
                $"Année invalide : {value}");
        _annee = value;
    }
}

Côté utilisateur

film.Annee = 2010;     // OK
film.Annee = -3000;    // ArgumentException
film.Annee = 99999;    // ArgumentException
1888 = année du premier film de l'histoire (Roundhay Garden Scene). Une règle métier transformée en code, à un seul endroit.
Sans le setter, cette règle serait éparpillée dans 20 endroits qui touchent film.Annee. Ou oubliée.
J1.29
Les niveaux d'accès en C#

Du plus ouvert au plus fermé. Règle d'or : commence par private, ouvre uniquement quand nécessaire.

publicVisible partout. C'est ton API publique, ton contrat avec l'extérieur.
privateVisible uniquement dans la classe. Défaut pour tout champ ou méthode interne.
protectedVisible dans la classe et ses classes filles. Utile pour l'héritage (J2).
internalVisible dans l'assembly (le projet). Pratique pour les classes utilitaires.
protected internalUnion des deux : assembly courant ou classes filles.
private protectedIntersection : classes filles uniquement dans le même assembly.
En pratique, 90 % du temps tu utilises public et private. protected arrive avec l'héritage. Les deux derniers sont rares.
J1.30
Encapsulation : les 4 règles à retenir

1. Champs privés

Tout champ est private par défaut. Pas de public string Titre; à la sauvage.

2. Propriétés publiques

L'accès passe par get / set. Le getter lit, le setter contrôle.

3. Validation centralisée

Les règles métier vivent dans le setter, pas dans 20 endroits qui assignent la valeur.

4. API minimale

Plus l'API publique est petite, plus le code évolue sans tout casser.

Question pour la suite : on a protégé les modifications. Mais comment garantir un état initial valide dès la création de l'objet ? C'est le rôle des constructeurs.

Syntaxe C# de l'héritage

Un seul opérateur : deux points (:) entre la classe et son parent.

La classe parente

class MediaItem
{

    public int Annee { get; set; }

    public void Afficher()
    {
        Console.WriteLine($"{Titre} ({Annee})");

}

La classe enfant

{
    public string Realisateur { get; set; }
}

J2.06
Membres hérités : qui descend, qui reste caché

L'enfant voit public et protected. Il ne voit jamais le private du parent.

MediaItem (parent)
public string Titre visible partout
protected int _annee visible dans Film, Série, etc.
private Guid _id visible UNIQUEMENT dans MediaItem
↓ héritage ↓
Film (enfant)
Titre accessible ✓
_annee accessible grâce à protected ✓
_id invisible ✗
Règle : si tu veux qu'un champ soit utilisable par les classes filles mais pas par l'extérieur, utilise protected. Sinon, garde private.
J2.07
Constructeurs et base()

Le constructeur du parent s'exécute toujours avant celui de l'enfant. base(...) lui passe les paramètres.

Le code

class MediaItem
{
    public string Titre { get; }

    public MediaItem(string titre)
    {
        Titre = titre;
    }
}

class Film : MediaItem
{
    public int Annee { get; }

    public Film(string titre, int annee)
        : base(titre)        // ← appel parent
    {
        Annee = annee;
    }
}

Ordre d'exécution

new Film("Inception", 2010)
↓
Film(...) : base("Inception")
↓ base() ↓
MediaItem("Inception")
Titre = "Inception"
↓ retour ↓
Film(...) continue
Annee = 2010
Sans base(...), C# appelle automatiquement le constructeur sans paramètre du parent. Si le parent n'en a pas, ça ne compile pas.

J2.12
virtual et override en C#

Le parent autorise l'override avec virtual. L'enfant remplace avec override. Explicite des deux côtés.

Parent : autorise

class MediaItem
{
    public string Titre { get; set; }

    public virtual void Afficher()
    {
        Console.WriteLine(
            $"{Titre} (média)");
    }
}

Enfant : remplace

class Film : MediaItem
{
    public string Realisateur { get; set; }

    public override void Afficher()
    {
        Console.WriteLine(
          $"🎬 {Titre} de {Realisateur}");
    }
}
Sans virtual dans le parent, le compilateur refuse override. C'est volontaire : tu décides ce qui peut être personnalisé.

J2.20
abstract vs virtual : quand quoi ?

virtual : optionnel

  • Le parent a un comportement par défaut
  • L'enfant peut le remplacer (override) ou non
  • Si l'enfant ne fait rien, il hérite du comportement du parent
public virtual void Afficher()
{
    Console.WriteLine(Titre);
}

abstract : obligatoire

  • Le parent n'a pas de comportement par défaut
  • L'enfant doit implémenter, sinon erreur de compilation
  • Force la classe parente à être abstract
public abstract void Afficher();
Règle pratique : si tu peux écrire une implémentation par défaut sensée, virtual. Sinon abstract.

J3.05
Choisir : héritage ou composition

Héritage si

  • "X est un Y" sonne juste
  • Vraie famille avec code commun
  • Le parent expose un comportement personnalisable par les enfants
  • Profondeur 1 ou 2 niveaux

Composition si

  • "X a un Y" sonne juste
  • Une capacité réutilisable par plusieurs familles
  • Tu veux pouvoir changer ou tester l'élément en isolation
  • Tu hésites
Favor composition over inheritance.

Définition

public class SoldeInsuffisantException
    : Exception
{

    public decimal MontantDemande { get; }

        decimal solde,
        decimal demande)
        : base($"Solde {solde:C} insuffisant " +
               $"pour retrait de {demande:C}")

        SoldeActuel = solde;
        MontantDemande = demande;
    }
}

Usage

public void Retirer(decimal montant)
{
    if (montant > _solde)
        throw new SoldeInsuffisantException(
            _solde, montant);
    _solde -= montant;
}

// Côté appelant
try { compte.Retirer(500); }
catch (SoldeInsuffisantException ex)
{
    var manque = ex.MontantDemande
                 - ex.SoldeActuel;

}

Catch silencieux

Tu masques tous les bugs. Si tu catch, fais quelque chose.

throw ex

{

    throw ex; // stack trace perdue
}

Utilise throw; sans argument pour préserver la stack.

Exception en flux normal

Utilise int.TryParse. Les exceptions coûtent cher.

Le pattern MVC

Trois rôles, une séparation claire. C'est SRP appliqué à l'architecture web.

Model

Les données et la logique métier. C'est la suite directe de ce que tu fais en console : tes classes du domaine, validation, calculs.

la cuisine

View

Le rendu HTML pour le navigateur. Pas de logique métier ici, juste la présentation et un peu de logique d'affichage.

la salle

L'orchestrateur. Reçoit la requête HTTP, demande au model, choisit la view, renvoie la réponse.

ASP.NET Core a un service container intégré. Tu enregistres tes services, le framework les injecte là où il faut.

J4.15
Créer un service

Un service, c'est une interface (le contrat) et une classe qui l'implémente. On l'écrit avant de l'enregistrer.

1. L'interface (le contrat)

public interface IVoitureService
{
    List<Voiture> Lister();
    Voiture? Trouver(int id);
    decimal CalculerTarif(
        Voiture v, int jours);
}

L'interface décrit ce que le service fait, jamais comment. C'est elle que les controllers demanderont.

2. L'implémentation

public class VoitureService : IVoitureService
{
    private readonly IVoitureRepository _repo;

    public VoitureService(
        IVoitureRepository repo)
    {
        _repo = repo;
    }

    public List<Voiture> Lister()
        => _repo.All();

    public Voiture? Trouver(int id)
        => _repo.All()
            .FirstOrDefault(v => v.Id == id);

    public decimal CalculerTarif(
        Voiture v, int jours)
        => v.TarifJournalier * jours;
}
La classe dépend de l'abstraction IVoitureRepository, pas d'une implémentation concrète → elle aussi sera injectée. Le DIP se propage en cascade. C'est ce VoitureService qu'on enregistre ensuite dans Program.cs.

J4.17
Lifetimes : Singleton, Scoped, Transient

Singleton

Une seule instance pour toute l'application. Créée au premier usage, vit jusqu'au shutdown.

Quand : caches, repositories en mémoire, services stateless globaux.

Attention : thread safety obligatoire si état mutable.

Scoped

Une instance par requête HTTP. Recréée à chaque requête, partagée entre les services d'une même requête.

Quand : DbContext, unit of work, contexte utilisateur.

Transient

Une nouvelle instance à chaque injection. Vie courte, pas d'état conservé.

Quand : services stateless légers, calculs simples.

En cas de doute, commence par Scoped. C'est le défaut le plus sûr pour la plupart des cas.

Une vraie base de données : SQLite

Le JSON dépanne, mais une appli sérieuse a besoin d'une base SQL. SQLite + Entity Framework Core = persistance robuste en quelques lignes.

J4.26
SQLite + EF Core, le duo

SQLite

Une base SQL dans un seul fichier (.db). Pas de serveur à installer ni à lancer.

Embarquée, zéro configuration. Parfaite pour le dev, le desktop et les petites applis web.

Même langage SQL que les grands : tu migres vers PostgreSQL plus tard sans réécrire ta logique.

Entity Framework Core

L'ORM officiel de .NET (Object-Relational Mapping).

Tu écris des classes C#, EF génère le SQL et crée les tables. Une classe ↔ une table, une propriété ↔ une colonne.

Les requêtes s'écrivent en LINQ : _db.Voitures.Where(v => v.Disponible).

Le DbContext : la porte vers la base
using Microsoft.EntityFrameworkCore;

public class AppDbContext : DbContext
{
    public AppDbContext(
        DbContextOptions<AppDbContext> options)
        : base(options) { }

    public DbSet<Voiture> Voitures
        => Set<Voiture>();

    public DbSet<Reservation> Reservations
        => Set<Reservation>();
}

À retenir

  • Chaque DbSet<T> correspond à une table.
  • Le constructeur reçoit les options (connection string) injectées par ASP.NET.
  • EF déduit colonnes et types à partir des propriétés de Voiture et Reservation.
J4.29
Relations : CarBrand → CarModel → Car

Deux relations un-à-plusieurs : une marque a plusieurs modèles, un modèle a plusieurs voitures. EF Core les déduit par convention.

Trois entités liées

public class CarBrand
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public List<CarModel> Models { get; set; } = new();
}

public class CarModel
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public int CarBrandId { get; set; }          // FK
    public CarBrand Brand { get; set; } = null!;
    public List<Car> Cars { get; set; } = new();
}

public class Car
{
    public int Id { get; set; }
    public string Plate { get; set; } = "";
    public int CarModelId { get; set; }          // FK
    public CarModel Model { get; set; } = null!;
}

Ce qu'EF Core en déduit

  • CarBrandId + la navigation Brand = clé étrangère détectée par convention.
  • Models / Cars (des List<>) = le côté « plusieurs ».
  • Trois DbSet<> à ajouter dans AppDbContext : CarBrands, CarModels, Cars.

Charger les entités liées

_db.Cars
   .Include(c => c.Model)
       .ThenInclude(m => m.Brand)
   .ToList();
dotnet ef migrations add Relations crée les tables et les clés étrangères automatiquement. Aucune écriture de SQL.

Styliser les vues : Tailwind CSS

Les vues Razor sortent du HTML brut. Tailwind apporte un design system cohérent sans écrire une ligne de CSS à la main.

J4.33
Pourquoi Tailwind & comment l'installer

Utility-first

Des classes utilitaires composées directement dans le HTML, pas de CSS à écrire à la main :

<button class="rounded bg-blue-600 px-4
        py-2 text-white hover:bg-blue-700">
    Réserver
</button>

Cohérence garantie, pas de fichiers CSS qui gonflent au fil du projet.

Deux méthodes

CDN (Play CDN) - une ligne, zéro build. Idéal pour démarrer et pour le bootcamp. Pas pour la prod.
CLI / build - génère un CSS purgé et optimisé. La vraie méthode de production (quelques Ko au final).
