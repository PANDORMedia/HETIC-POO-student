SOLID : LSP, ISP & DIP

slidesDurée : 30 min

Cette leçon couvre les trois derniers principes SOLID : LSP (substitution de Liskov), ISP (segregation des interfaces) et DIP (inversion des dépendances). Chacun vise un même objectif : limiter le couplage et garder un code qui reste testable et modifiable.

LSP : substituer sans surprise

Une instance de classe fille doit pouvoir remplacer une instance de la classe parente sans casser le code qui appelle. Si remplacer le parent par l'enfant change le comportement attendu, le principe est viole.

Violation : Carre hérite de Rectangle

class Rectangle
{
    public virtual int Largeur { get; set; }
    public virtual int Hauteur { get; set; }
}

class Carre : Rectangle
{
    public override int Largeur
    {
        set { base.Largeur = value; base.Hauteur = value; }
    }
    // ... idem pour Hauteur
}

Le code qui dépend de Rectangle se comporte mal des qu'on lui passe un Carre :

void Test(Rectangle r)
{
    r.Largeur = 4;
    r.Hauteur = 5;
    Console.WriteLine(r.Largeur * r.Hauteur);
    // Attendu : 20
    // Recoit un Carre : 25
}

Le bug est silencieux : rien ne plante, mais le résultat est faux. C'est exactement ce que LSP cherche à éviter.

La bonne abstraction

Hériter juste pour économiser deux champs ne vaut pas une violation LSP. Une interface partagée fait mieux le travail.

interface IForme
{
    int CalculerAire();
}

class Rectangle : IForme
{
    public int Largeur { get; set; }
    public int Hauteur { get; set; }
    public int CalculerAire() => Largeur * Hauteur;
}

class Carre : IForme
{
    public int Cote { get; set; }
    public int CalculerAire() => Cote * Cote;
}

Pas d'héritage entre Carre et Rectangle. L'interface suffit pour le polymorphisme, et aucune des deux classes ne ment sur son comportement.

ISP : interfaces fines

Mieux vaut plusieurs petites interfaces qu'une seule grosse. Personne ne devrait avoir a implémenter des méthodes qu'il n'utilise pas.

Interface fourre-tout

interface IMachine
{
    void Imprimer(...);
    void Scanner(...);
    void Faxer(...);
    void Photocopier(...);
}

class ImprimanteSimple : IMachine
{
    public void Imprimer(...) { ... }
    public void Scanner(...) { throw new NotImplementedException(); }
    public void Faxer(...) { throw new NotImplementedException(); }
    public void Photocopier(...) { throw new NotImplementedException(); }
}

Une imprimante simple doit déclarer des méthodes qu'elle ne sait pas faire et lever des exceptions. C'est un signe clair que l'interface est trop large.

Interfaces segmentées

interface IImprime { void Imprimer(...); }
interface IScan { void Scanner(...); }
interface IFax { void Faxer(...); }

class ImprimanteSimple : IImprime { ... }
class MultiFonctions : IImprime, IScan, IFax { ... }

Chaque classe implémente exactement les contrats qu'elle remplit. Une classe peut en combiner plusieurs quand elle en a besoin.

DIP : dépendre des abstractions

Les modules de haut niveau ne doivent pas dépendre des modules de bas niveau. Les deux doivent dépendre d'abstractions.

Couplage direct

class CommandeService
{
    private SqlServerRepository _repo = new SqlServerRepository();

    public void Valider(Commande c)
    {
        _repo.Sauver(c);
    }
}

Ici le service crée lui-même sa dépendance concrète. Impossible de le tester sans SQL Server, et impossible de changer de base de données sans toucher au service.

Dépendance inversée

interface IRepository<T>
{
    void Sauver(T entity);
}

class CommandeService
{
    private IRepository<Commande> _repo;

    public CommandeService(IRepository<Commande> repo)
    {
        _repo = repo;
    }
}

Le service dépend d'une abstraction. On lui injecte l'implémentation depuis l'extérieur, ce qui rend les tests et le changement de base de données triviaux.

L'inversion des flèches

Avant, le haut niveau connaissait directement le bas niveau :

  • CommandeService (haut niveau) dépend de SqlServerRepository (bas niveau).
  • Couplage rigide : le haut connait le bas.

Après, c'est l'abstraction qui est au centre :

  • CommandeService dépend de IRepository (abstraction).
  • SqlServerRepository implémente IRepository.
  • Les deux dépendent de l'abstraction, et c'est le bas niveau qui implémente.

À retenir

PrincipeIdéeSignal d'alerte
