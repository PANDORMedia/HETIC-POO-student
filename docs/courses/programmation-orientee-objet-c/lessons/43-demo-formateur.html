Démo guidée : composition, SOLID et exceptions

codingDurée : 25 min

Cette demo guidee rassemble trois themes du module : la composition opposee à l'héritage, les principes SOLID et la gestion des exceptions. Tu peux la suivre seul, étape par étape, en lisant le code et en le reproduisant. Deux projets du dépôt servent de support : demos/composition-logger pour la composition et l'injection de dépendances, et demos/location-voiture pour les principes SOLID appliques a un calcul de tarif.

Objectif

À la fin de cette étape, tu dois savoir choisir entre héritage et composition, reconnaître une violation de SRP, OCP ou DIP, et écrire une exception métier propre. Le but n'est pas de retenir des définitions mais de relier chaque principe a un problème concret de couplage ou de testabilité.

Étape 1 : composition contre héritage

L'héritage exprime une relation is-a : une classe specialise une autre et en réutilise le comportement.

class Voiture : Vehicule
{
    public void Demarrer() { ... }
}

var v = new Voiture();
v.Demarrer(); // Voiture est un Vehicule

La composition exprime une relation has-a : une classe contient un objet et lui délègue une partie du travail.

class Voiture
{
    private Moteur _moteur;

    public Voiture(Moteur m)
    {
        _moteur = m;
    }

    public void Demarrer()
    {
        _moteur.Demarrer();
    }
}

Ici la Voiture a un Moteur et lui délègue le démarrage. La composition couplé moins fortement les classes que l'héritage : tu peux remplacer le Moteur sans modifier la Voiture. C'est ce que montre le projet demos/composition-logger, ou un service reçoit son logger par le constructeur plutôt que d'en hériter.

Étape 2 : SRP, une seule responsabilité

Une classe doit avoir une seule raison de changer. La version ci-dessous en a quatre : la règle métier, le schéma de base de données, la configuration SMTP et la mise en page.

// Mauvais : quatre responsabilites
class Facture
{
    public void Calculer() { ... }
    public void SauverEnBase() { ... }
    public void EnvoyerParMail() { ... }
    public string GenererPdf() { ... }
}

On séparé chaque responsabilité dans sa propre classe. Chacune evolue alors indépendamment.

class Facture
{
    public void Calculer() { ... }
}

class FactureRepository
{
    public void Sauver(...) { ... }
}

class FactureMailer
{
    public void Envoyer(...) { ... }
}

class FacturePdfGenerator
{
    public string Generer(...) { ... }
}

Étape 3 : OCP, ouvert à l'extension

Tu dois pouvoir ajouter un comportement sans toucher au code qui fonctionne déjà. La cascade de if ci-dessous viole ce principe : ajouter un tarif oblige a modifier la méthode existante.

// Violation : ajouter un tarif modifie cette methode
class CalculTarif
{
    public decimal Calculer(string type)
    {
        if (type == "standard") return ...;
        else if (type == "weekend") return ...;
        else if (type == "promo") return ...;
    }
}

En passant par une interface, chaque tarif devient une classe a part. Ajouter un tarif revient a créer une classe, et aucune ligne existante ne change.

interface ITarif
{
    decimal Calculer(...);
}

class TarifStandard : ITarif { ... }
class TarifWeekend : ITarif { ... }
class TarifPromo : ITarif { ... }

Le projet demos/location-voiture applique exactement ce schéma : le calcul du prix de location s'appuie sur une interface de tarif, et chaque type de tarif vit dans sa propre implémentation.

Étape 4 : DIP, dépendre des abstractions

Les modules de haut niveau ne doivent pas dépendre des modules de bas niveau. Les deux dépendent d'abstractions. Le couplage direct ci-dessous rend le service impossible à tester sans SQL Server et impossible à faire évoluer sans le modifier.

// Couplage direct
class CommandeService
{
    private SqlServerRepository _repo = new SqlServerRepository();

    public void Valider(Commande c)
    {
        _repo.Sauver(c);
    }
}

On inverse la dépendance : le service reçoit une abstraction par le constructeur, et tu lui injectes l'implémentation de ton choix.

interface IRepository<T>
{
    void Sauver(T entity);
}

class CommandeService
{
    private IRepository<Commande> _repo;

    public CommandeService(IRepository<Commande> repo)
    {
        _repo = repo;
    }
}

Le service dépend désormais d'une interface. En test, tu lui passes une fausse implémentation en mémoire ; en production, une implémentation SQL.

Étape 5 : try / catch / finally

La gestion d'erreur structure le flux quand une opération peut échouer.

FileStream stream = null;
try
{
    stream = File.Open(chemin);
    Traiter(stream);
}
catch (FileNotFoundException ex)
{
    Log.Warn($"Fichier absent : {chemin}");
}
catch (IOException ex)
{
    Log.Error("Erreur IO", ex);
    throw;
}
finally
{
    stream?.Close();
}

Quatre règles à retenir :

  • Plusieurs catch sont ordonnes du plus spécifique au plus général.
  • finally s'exécute toujours, même après un throw ou un return.
  • throw; sans argument relance l'exception en gardant la pile d'appels.
  • using remplace souvent try / finally pour les objets IDisposable.

Étape 6 : créer une exception métier

Une exception métier porte des données utiles à l'appelant. Ici, le solde disponible et le montant demande sont exposés en propriétés.

public class SoldeInsuffisantException : Exception
{
    public decimal SoldeActuel { get; }
    public decimal MontantDemande { get; }

    public SoldeInsuffisantException(decimal solde, decimal demande)
        : base($"Solde {solde:C} insuffisant pour retrait de {demande:C}")
    {
        SoldeActuel = solde;
        MontantDemande = demande;
    }
}

On la lève au moment où la règle métier est violee, puis on l'attrape là où l'on sait comment réagir.

public void Retirer(decimal montant)
{
    if (montant > _solde)
        throw new SoldeInsuffisantException(_solde, montant);

    _solde -= montant;
}

// Cote appelant
try
{
    compte.Retirer(500);
}
catch (SoldeInsuffisantException ex)
{
    var manque = ex.MontantDemande - ex.SoldeActuel;
    Console.WriteLine($"Manque {manque:C}");
}
