Exceptions orientées objet

readingDurée : 20 min

Quand une opération ne peut pas continuer

Une exception est le mécanisme qui permet a une opération de signaler qu'elle ne peut pas aller au bout de ce qu'on lui demande. Plutôt que de renvoyer une valeur ambigue ou de poursuivre dans un état incoherent, l'opération lance un signal type. Le code qui appelle décide alors quoi faire : reessayer, prevenir l'utilisateur, écrire un message dans le journal, ou laisser le problème remonter plus haut.

L'intérêt de cette approche est qu'elle séparé nettement deux responsabilités : le code qui détecte un problème n'est pas toujours celui qui sait comment le resoudre. L'exception transporte l'information de l'un vers l'autre.

Pourquoi des exceptions plutôt que des codes de retour ?

Le style historique, hérite du C, consiste à renvoyer un code numérique qui indique le succès ou la nature de l'echec. L'appelant doit ensuite tester ce code à la main.

int result = ouvrirFichier(chemin);
if (result == ERR_NOT_FOUND) { ... }
else if (result == ERR_PERMISSION) { ... }
else if (result < 0) { ... }

// Si tu oublies de verifier, ton code
// continue en silence avec un etat pourri.

Le défaut majeur de ce modèle est qu'il repose entierement sur la discipline de l'appelant. Si une vérification est oubliée, le programme continue avec une valeur fausse et le bug se manifeste bien plus tard, loin de sa cause réelle.

Avec les exceptions, la situation s'inverse : l'echec ne peut pas être ignore en silence.

try
{
    var stream = File.Open(chemin);
}
catch (FileNotFoundException ex) { ... }
catch (UnauthorizedAccessException ex) { ... }

// Si tu oublies le catch, l'exception remonte.
// Impossible de l'ignorer en silence.

Une exception est un objet a part entière. Elle porte un type, un message lisible, une stack trace qui indique le chemin d'appels suivi jusqu'au point de declenchement, et éventuellement une innerException qui conserve la cause d'origine quand une erreur en enveloppe une autre.

Le principe : détecter ici, traiter ailleurs

On peut resumer le fonctionnement par une image simple. Un cuisinier qui constate un début d'incendie ne se débrouille pas seul : il déclenche l'alarme, et quelqu'un d'autre, équipe pour cela, s'en occupe. Le code suit le même decoupage.

  • Le code qui détecte le problème exécute un throw.
  • L'exception se propage dans la pile d'appels, traversant les méthodes qui ne savent pas la traiter.
  • Un catch l'intercepte là où se trouve le code qui sait quoi faire.

Entre les deux, l'objet exception transporte toute l'information utile : son type, son message et le contexte de l'erreur.

La hiérarchie des exceptions en .NET

Toutes les exceptions derivent d'une classe racine commune, Exception. Cette organisation par héritage est ce qui permet d'attraper soit un type très précis, soit une famille entière.

  • Exception est la racine de toute la hiérarchie.
  • SystemException regroupe les erreurs techniques courantes : NullReferenceException, IndexOutOfRangeException, InvalidOperationException.
  • La famille des arguments invalides : ArgumentException, ArgumentNullException, ArgumentOutOfRangeException.
  • Les erreurs d'entrée-sortie : IOException, FileNotFoundException, DirectoryNotFoundException.
  • Tes exceptions métier, comme VehiculeIndisponibleException ou SoldeInsuffisantException.

Tes exceptions métier héritent de Exception. Par convention, leur nom se terminé par le suffixe "Exception". On leur donne un constructeur qui accepte un message clair, et idéalement une innerException pour conserver une cause sous-jacente.

La syntaxe try / catch / finally

FileStream stream = null;
try
{
    stream = File.Open(chemin);
    Traiter(stream);
}
catch (FileNotFoundException ex)
{
    Log.Warn($"Fichier absent : {chemin}");
}
catch (IOException ex)
{
    Log.Error("Erreur IO", ex);
    throw;
}
finally
{
    stream?.Close();
}

Quelques règles structurent ce bloc :

  • On peut enchainer plusieurs catch, du plus spécifique au plus général. Le premier qui correspond au type de l'exception est retenu, donc l'ordre compte.
  • Le bloc finally s'exécute toujours, même après un throw ou un return. C'est l'endroit idéal pour liberer une ressource.
  • Un throw; sans argument re-lance l'exception en cours en preservant la stack trace d'origine.
  • Pour les objets IDisposable, le using remplace souvent le couplé try / finally et garantit la liberation de la ressource.

Créer une exception métier

Définir un type d'exception propre à ton domaine presente deux avantages : l'appelant peut l'attraper de façon ciblee, et l'objet peut transporter des données structurees au-delà du simple message.

public class SoldeInsuffisantException : Exception
{
    public decimal SoldeActuel { get; }
    public decimal MontantDemande { get; }

    public SoldeInsuffisantException(
        decimal solde, decimal demande)
        : base($"Solde {solde:C} insuffisant " +
               $"pour retrait de {demande:C}")
    {
        SoldeActuel = solde;
        MontantDemande = demande;
    }
}

L'exception est levée au moment où la règle métier est violee, et non laissee à la charge de l'appelant.

public void Retirer(decimal montant)
{
    if (montant > _solde)
        throw new SoldeInsuffisantException(
            _solde, montant);
    _solde -= montant;
}

Cote appelant, on attrape ce type précis et on exploite les propriétés qu'il porte pour produire un message utile.

try
{
    compte.Retirer(500);
}
catch (SoldeInsuffisantException ex)
{
    var manque = ex.MontantDemande - ex.SoldeActuel;
    Console.WriteLine($"Manque {manque:C}");
}

Les anti-patterns a éviter

Les exceptions sont mal utilisées aussi souvent qu'elles sont utiles. Voici les erreurs les plus frequentes.

Le catch silencieux

try { ... }
catch { /* nothing */ }

Attraper une exception sans rien faire masque tous les bugs. Si tu attrapes, fais quelque chose : journaliser, corriger, ou re-lancer.

Le throw ex qui perd la trace

catch (Exception ex)
{
    Log(ex);
    throw ex; // stack trace perdue
}

Re-lancer avec throw ex; reinitialise la stack trace et fait perdre l'origine réelle de l'erreur. Utilise throw; sans argument pour la préserver.

L'exception en flux normal

try { return int.Parse(s); }
catch { return 0; }

Les exceptions ont un coût d'exécution non negligeable. Elles ne doivent pas servir de logique de contrôle ordinaire. Ici, int.TryParse exprime la même intention sans déclencher d'exception.

L'exception trop générique

throw new Exception(
    "Solde insuffisant");

Lancer une Exception brute oblige l'appelant a tout attraper sans distinction. Crée un type métier dédié : il pourra alors être attrape de façon spécifique, ce qui rend le code appelant plus clair et plus sur.

À retenir

  • Une exception est un objet type qui signale qu'une opération ne peut pas continuer.
  • Elle ne peut pas être ignoree en silence, contrairement a un code de retour oublie.
  • Le code qui détecte le problème et celui qui le traite sont séparés par la propagation dans la pile d'appels.
  • Tes exceptions métier héritent de Exception, portent un suffixe "Exception" et peuvent transporter des données utiles.
  • Range tes catch du plus spécifique au plus général, libéré les ressources dans finally ou avec using, et re-lance avec throw; pour garder la stack trace.
