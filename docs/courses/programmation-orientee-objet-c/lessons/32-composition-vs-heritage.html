Composition vs Héritage

readingDurée : 20 min

Solidifier l'architecture

L'héritage est un outil utile, mais il ne répond pas à tous les besoins. Au début d'un projet, ranger une classe sous un parent commun paraît naturel et économe en code. Puis la hiérarchie grossit, certaines classes filles doivent ignorer une partie du comportement parent, et la même logique se retrouve copiée d'une famille à l'autre. À ce stade, l'héritage ne simplifie plus, il rigidifie. La réponse consiste à composer : ranger les capacités dans des objets séparés, puis les assembler dans la classe qui en a besoin.

Cette leçon explique quand l'héritage atteint ses limites, ce que la composition apporte, et comment choisir entre les deux sans hésiter.

Quand l'héritage atteint ses limites

Plusieurs symptômes signalent qu'une hiérarchie de classes est devenue un poids plutôt qu'un appui. Il est utile de les reconnaître tôt, avant que le code ne devienne difficile à modifier.

  • Une hiérarchie de quatre niveaux ou plus, où l'on ne sait plus quelle classe définit quel comportement.
  • Une classe fille qui doit ignorer ou neutraliser du comportement hérité du parent, signe qu'elle n'appartient pas vraiment à cette famille.
  • Du copier-coller entre des classes de familles différentes, parce que la capacité partagée ne trouve pas sa place dans l'arbre d'héritage.
  • Un override qui appelle base puis ajoute trois fois la même logique, au lieu de réutiliser un objet dédié.

Le remède est le même dans tous ces cas : extraire les capacités dans des objets séparés, les composer dans la classe concernée, et réutiliser sans hériter. Une voiture a un moteur ; elle n'est pas un moteur. Cette distinction entre avoir et être est au coeur du choix.

La voiture et ses pièces

La métaphore de la voiture rend la différence concrète. Une voiture est un véhicule : voilà une relation d'héritage, un is-a. En revanche, une voiture a un moteur, a une boîte de vitesses, a un châssis et a quatre roues : ce sont des relations de composition, des has-a.

Cette organisation apporte trois avantages directs :

  • Tu changes le moteur sans changer la voiture, parce que la voiture dépend du rôle du moteur, pas de sa fabrication interne.
  • Tu testes le moteur en isolation, comme une unité autonome, sans monter toute la voiture autour.
  • Tu réutilises le moteur dans un autre véhicule, car il ne dépend pas de la classe qui le contient.

Là où l'héritage figé une pièce dans une famille unique, la composition la rend mobile et réutilisable.

Syntaxe : héritage contre composition

Comparons les deux écritures sur le même exemple. Avec l'héritage, la voiture étend une classe Vehicule et reçoit son comportement par filiation.

// Héritage (is-a)
class Voiture : Vehicule
{
    public void Demarrer()
    {
        // ...
    }
}

var v = new Voiture();
v.Demarrer();
// Voiture est un Vehicule.

Avec la composition, la voiture détient un Moteur qu'elle reçoit dans son constructeur, et lui délègue le démarrage. La voiture ne sait pas comment le moteur démarre ; elle se contente de lui transmettre la demande.

// Composition (has-a)
class Voiture
{
    private Moteur _moteur;

    public Voiture(Moteur m)
    {
        _moteur = m;
    }

    public void Demarrer()
    {
        _moteur.Demarrer();
    }
}
// Voiture a un Moteur, lui délègue le démarrage.

Le détail à remarquer est le passage du moteur dans le constructeur. La voiture ne crée pas elle-même son moteur : elle le reçoit. Cela permet d'injecter un moteur réel en production et un moteur de test en vérification, sans modifier la classe Voiture.

Choisir : héritage ou composition

Le choix se fait en lisant la relation à voix haute. La formulation qui sonne juste indique l'outil approprié.

Privilégie l'héritage quand :

  • La phrase "X est un Y" sonne juste et reste vraie en toutes circonstances.
  • Il s'agit d'une vraie famille avec du code commun partagé par tous les membres.
  • Le parent expose un comportement destiné à être personnalisé par les enfants.
  • La profondeur reste limitée à un ou deux niveaux.

Privilégie la composition quand :

  • La phrase "X a un Y" sonne juste, c'est-à-dire que Y est une capacité que X possède.
  • Cette capacité est réutilisable par plusieurs familles de classes.
  • Tu veux pouvoir changer ou tester l'élément en isolation, indépendamment de son conteneur.

Et si tu hésites encore, une règle simple tranche : préfère la composition à l'héritage. La composition reste flexible quand le besoin évolue, alors qu'une hiérarchie trop profonde devient coûteuse à défaire. L'héritage se mérite ; la composition se choisit par défaut.
