Quiz : SOLID & Exceptions

quizDurée : 20 min

Ce quiz revient sur les cinq principes SOLID et sur la gestion des exceptions en .NET. Pour chaque question, une seule réponse est correcte. Prends le temps de relire l'explication, elle résumé le point à retenir.

QCM1 min

Que signifie le principe SRP (Single Responsibility) ?

  1. Une classe ne doit avoir qu'une seule méthode publique
  2. Une classe ne doit avoir qu'une seule raison de changer
  3. Une classe ne doit dépendre que d'une seule autre classe
  4. Une classe ne doit être instanciée qu'une seule fois
Explication

SRP demande qu'une classe porte une seule responsabilité, donc une seule raison de changer. Une classe Facture qui calcule, sauve en base, envoie un mail et génère un PDF cumule quatre raisons de changer : on la decoupe en classes dédiées.

QCM1 min

Le principe OCP (Open/Closed) dit qu'une classe doit être :

  1. Ouverte à la modification, fermée à l'extension
  2. Fermée à l'extension et à la modification
  3. Ouverte à l'extension, fermée à la modification
  4. Ouverte à l'extension et à la modification
Explication

OCP veut qu'on ajoute du comportement sans toucher au code qui marche déjà. Au lieu d'allonger une chaine de if dans CalculTarif, on définit une interface ITarif et chaque nouveau tarif devient une nouvelle classe. Aucune ligne existante ne change.

QCM1 min

Dans l'exemple ou Carre hérite de Rectangle, quel principe est viole ?

  1. LSP (Liskov Substitution)
  2. SRP (Single Responsibility)
  3. ISP (Interface Segregation)
  4. DIP (Dependency Inversion)
Explication

LSP exige qu'une instance de fille remplace une instance de parent sans surprise. Quand on passe un Carre là où un Rectangle est attendu, fixer la largeur a 4 et la hauteur a 5 donne une aire de 25 au lieu de 20. Le code qui dépend de Rectangle casse silencieusement.

QCM1 min

Une ImprimanteSimple qui implémente IMachine et lève NotImplementedException pour Scanner, Faxer et Photocopier viole quel principe ?

  1. OCP (Open/Closed)
  2. LSP (Liskov Substitution)
  3. ISP (Interface Segregation)
  4. SRP (Single Responsibility)
Explication

ISP demande plusieurs petites interfaces plutôt qu'une grosse, pour que personne n'implémente des méthodes qu'il n'utilise pas. En segmentant en IImprime, IScan et IFax, l'imprimante simple ne porte que le contrat qu'elle remplit vraiment.

QCM1 min

Comment le principe DIP (Dependency Inversion) corrige-t-il un CommandeService couplé a SqlServerRepository ?

  1. En rendant SqlServerRepository statique
  2. En dependant de l'abstraction IRepository<Commande> injectée dans le constructeur
  3. En instanciant SqlServerRepository dans chaque méthode
  4. En héritant de SqlServerRepository
Explication

DIP veut que les modules haut niveau dépendent d'abstractions, pas d'implémentations. Le service reçoit une IRepository<Commande> par son constructeur : on lui injecte l'implémentation voulue, ce qui rend les tests possibles et permet de changer de base sans toucher au service.

QCM1 min

De quoi devraient hériter tes exceptions métier comme SoldeInsuffisantException ?

  1. De SystemException
  2. De InvalidOperationException
  3. De Exception
  4. De ArgumentException
Explication

Les exceptions métier héritent de Exception, portent un suffixe en "Exception" et exposent un constructeur acceptant un message, idéalement une innerException. Les types comme SystemException ou ArgumentException sont reserves au runtime et aux erreurs d'arguments.

QCM1 min

Que se passe-t-il avec le bloc finally dans un try / catch / finally ?

  1. Il ne s'exécute que si aucune exception n'est levée
  2. Il ne s'exécute que si une exception est levée
  3. Il est ignore après un return
  4. Il s'exécute toujours, même après un throw ou un return
Explication

Le bloc finally s'exécute dans tous les cas, ce qui en fait l'endroit idéal pour liberer une ressource (par exemple stream?.Close()). On enchaine les catch du plus spécifique au plus général, et using remplace souvent ce schéma pour les IDisposable.

QCM1 min

Pour relancer une exception captee sans perdre la stack trace, on écrit :

  1. throw; sans argument
  2. throw ex;
  3. throw new Exception(ex.Message);
  4. rien, on laisse le catch vide
Explication

throw; sans argument re-lance l'exception en preservant la stack trace d'origine. Écrire throw ex; reinitialise la pile et masque l'endroit réel de l'erreur. Le catch vide est un anti-pattern : il masque tous les bugs.
