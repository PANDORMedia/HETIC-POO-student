Projet fil rouge : guide complet

readingDurée : 20 min

Le projet fil rouge

Tu reprends la flotte de location que tu as modélisée en console et tu la fais vivre sur le web avec ASP.NET Core MVC. L'objectif n'est pas de tout réécrire : ton domaine existe déjà, il est teste, il est correct. Le travail consiste à l'envelopper dans une application web propre, organisee en couches, ou chaque responsabilité est a sa place.

Ce guide déroule le projet phase par phase. Chaque phase produit quelque chose qui tourne, et chaque phase prépare la suivante. Tu peux suivre l'énoncé complet du dépôt en parallèle, et regarder la demo aspnet-mvc pour voir une structure de référence déjà construite.

Le perimetre

L'application doit offrir les fonctionnalités suivantes :

  • la liste de la flotte ;
  • le detail d'un vehicule (sa fiche) ;
  • l'ajout, la modification et la suppression d'une voiture via des formulaires ;
  • la reservation d'une voiture avec calcul du tarif.

Trois contraintes encadrent ce perimetre. D'abord, tu réutilises tes classes du domaine (Vehicule, Voiture, Moto, etc.) sans les modifier : le domaine ne doit dépendre de rien qui touche au web. Ensuite, la persistance se fait en JSON sur le disque, pour que les données survivent a un redémarrage. Enfin, la validation se fait cote serveur, et l'injection de dépendances est utilisée partout où elle a un intérêt.

L'architecture en couches

L'application s'organise en quatre couches superposees. Chaque couche ne connait que l'abstraction de la couche du dessous, jamais son implémentation concrète. C'est l'application directe du principe d'inversion des dépendances (DIP).

L'intérêt de cette séparation est concret : tu pourras remplacer la persistance JSON par une base SQL plus tard sans toucher aux contrôleurs ni au domaine. Il suffira de fournir une autre implémentation de IVoitureRepository.

Phase 1 : Setup

Tu créés le squelette du projet et tu y deplaces ton domaine.

dotnet new mvc -n LocationWeb
cd LocationWeb

Crée un dossier Domain/ dans le projet et copies-y tes classes de l'exercice console : Vehicule (abstract), Voiture, Moto, Camionnette, les interfaces IAssurable et IRevisable, puis Reservation, ITarifCalculator, TarifStandard, TarifWeekend et VehiculeIndisponibleException. Vérifie que le projet compile et que dotnet run lance le site avec sa page d'accueil par défaut.

Phase 2 : Lecture

Tu affiches la flotte sans pouvoir encore la modifier. A ce stade, les données sont en dur, le temps de mettre en place les vues.

  1. Dans Controllers/, crée VoituresController. Pour cette phase, il porte une List<Voiture> statique avec trois ou quatre voitures.
  2. L'action Index() retourne la liste. La vue Razor Views/Voitures/Index.cshtml affiche cette liste avec un lien vers le detail de chaque voiture.
  3. L'action Detail(int id) retourne une voiture précise ou NotFound(). La vue Views/Voitures/Detail.cshtml affiche la fiche.
  4. Ajoute un lien vers /Voitures dans _Layout.cshtml, dans le menu en haut de page.

Phase 3 : Écriture

Tu ajoutes la création, la modification et la suppression de voitures via des formulaires. C'est ici qu'apparait le premier ViewModel, distinct du domaine, pour porter la saisie et ses règles de validation.

public class VoitureFormVm
{
    public int Id { get; set; }

    [Required(ErrorMessage = "Marque requise")]
    [StringLength(50)]
    public string Marque { get; set; }

    [Required]
    [StringLength(50)]
    public string Modele { get; set; }

    [Range(1, 9999)]
    public decimal TarifJournee { get; set; }

    [Range(1, 9)]
    public int NbPlaces { get; set; }

    [Required]
    public string TypeCarburant { get; set; }
}
  • Create() en GET retourne la vue avec un formulaire vide. Create(VoitureFormVm form) en POST valide via ModelState.IsValid ; en cas d'erreur, il re-rend la vue avec les messages, sinon il ajoute la voiture et redirige vers Index.
  • Edit(int id) en GET pre-remplit le formulaire avec la voiture existante. Edit(int id, VoitureFormVm form) en POST valide, applique les changements et redirige.
  • Delete(int id) en GET affiche une page de confirmation. Delete(int id, IFormCollection _) en POST supprime et redirige vers Index.
  • Crée les vues Create.cshtml, Edit.cshtml et Delete.cshtml en utilisant asp-for, asp-validation-for et asp-action.

Phase 4 : Injection de dépendances et persistance JSON

Tu sors la liste du contrôleur pour la placer derrière une interface. C'est le coeur de l'architecture : à partir d'ici, le contrôleur ne connait plus le stockage, seulement un service.

public interface IVoitureRepository
{
    IEnumerable<Voiture> Lister();
    Voiture LirePar(int id);
    void Ajouter(Voiture voiture);
    void Mettre(int id, Voiture voiture);
    void Supprimer(int id);
}
  1. Crée Services/VoitureRepositoryJson.cs qui implémente cette interface et lit ou écrit dans App_Data/voitures.json. Au démarrage, il charge le fichier s'il est présent, sinon il part d'une liste vide. À chaque ajout, modification ou suppression, il réécrit le fichier. Utilise System.Text.Json.JsonSerializer. Le Vehicule étant abstract, serialise uniquement la classe concrète Voiture a cette étape.
  2. Crée IVoitureService et VoitureService. Le service reçoit un IVoitureRepository dans son constructeur et expose les mêmes opérations, plus la logique métier propre à l'application, comme le mapping du ViewModel vers le domaine.
  3. Dans Program.cs, enregistre les services :
builder.Services.AddSingleton<IVoitureRepository, VoitureRepositoryJson>();
builder.Services.AddScoped<IVoitureService, VoitureService>();

VoituresController reçoit alors IVoitureService dans son constructeur et s'en sert. Il ne reste plus aucune liste statique dans le contrôleur. Vérifie qu'un redémarrage du serveur conserve les voitures ajoutées : c'est la persistance JSON qui fait son travail.

Phase 5 : Reservation

Tu permets a un utilisateur de reserver une voiture sur une période, avec calcul du tarif via une stratégie injectée.

public class ReservationFormVm
{
    [Required]
    public int VoitureId { get; set; }

    [Required, StringLength(100)]
    public string Client { get; set; }

    [Required, DataType(DataType.Date)]
    public DateTime DateDebut { get; set; }

    [Required, DataType(DataType.Date)]
    public DateTime DateFin { get; set; }
}
  1. Crée ReservationsController avec deux actions. Reserver(int voitureId) en GET affiche le formulaire pre-rempli avec la voiture. Reserver(ReservationFormVm form) en POST valide la saisie, construit une Reservation, calcule le montant total via un ITarifCalculator injecte, puis affiche une page de confirmation.
  2. Enregistre ITarifCalculator dans Program.cs. Choisis TarifStandard par défaut : le choix de la stratégie passe uniquement par l'injection de dépendances.
  3. Si la voiture est indisponible au moment de la confirmation, VehiculeIndisponibleException remonte. Attrape-la dans l'action et renvoie une page d'erreur lisible.

Bonus

Une fois les cinq phases atteintes, tu peux enrichir l'application :

  • une pagination simple sur l'index, par exemple dix voitures par page ;
  • une recherche par marque et modèle via un formulaire en haut de l'index ;
  • l'extension de la persistance aux Moto et Camionnette en gérant le polymorphisme JSON (un champ Type dans le JSON et une désérialisation sur mesure) ;
  • une seconde implémentation TarifWeekend, avec le choix de la stratégie propose dans le formulaire de reservation ;
  • une mise en forme avec Bootstrap, déjà inclus dans le template MVC par défaut.

Critères d'évaluation

Fonctionnel

  • l'application tourne sur localhost ;
  • les phases 1 a 4 sont atteintes au minimum ;
  • le CRUD complet sur Voiture fonctionne via les formulaires ;
  • la persistance JSON survit au redémarrage du serveur.

Architecture

  • le dossier Domain/ est réutilise tel quel, sans annotation web ni dépendance ASP.NET ;
  • IVoitureRepository et IVoitureService sont injectes via leurs interfaces ;
  • aucune logique métier ni accès direct au stockage dans les contrôleurs ;
  • la validation est faite cote serveur via DataAnnotations et ModelState.IsValid ;
  • au moins un ViewModel est distinct des classes du domaine.

Code

  • pas d'exception générique lancée ou attrapée ;
  • pas de catch silencieux ;
  • champs privés, propriétés publiques, encapsulation respectée.
