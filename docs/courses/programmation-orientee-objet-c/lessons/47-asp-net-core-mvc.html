ASP.NET Core MVC

readingDurée : 20 min

ASP.NET Core en bref

ASP.NET Core est le framework web de la plateforme .NET. Il est cross-platform, open source sur GitHub depuis 2014, et il sert le trafic HTTP via le serveur Kestrel intégré. Son pipeline de middleware est extensible : chaque étape (authentification, fichiers statiques, routage) s'ajoute comme un maillon que la requête traverse avant d'atteindre ton code.

Sur cette base, on peut construire plusieurs types d'applications : des API REST, des applications web MVC (notre choix ici), des Razor Pages, du Blazor, ou encore du gRPC et du SignalR. L'intérêt pour toi est que tu connais déjà la moitié du sujet. Le .NET 8, le SDK, le CLI dotnet et tes classes C# sont les mêmes que ceux utilises jusqu'à présent. ASP.NET Core ajoute simplement le contrat HTTP par-dessus ces fondations.

Anatomie d'un projet MVC

Un projet MVC suit une structure de dossiers conventionnelle. Cette organisation n'est pas decorative : elle reflete la séparation des rôles que nous detaillerons plus bas.

  • Controllers/ : les classes qui orchestrent les requêtes, par exemple HomeController.cs et VoituresController.cs.
  • Models/ : les classes du domaine, comme Voiture.cs.
  • Views/ : les fichiers .cshtml qui produisent le HTML, regroupés par contrôleur (Home/, Voitures/), plus un dossier Shared/ qui contient le gabarit commun _Layout.cshtml.
  • wwwroot/ : les ressources statiques (css, js, lib).
  • Program.cs, appsettings.json et le fichier .csproj à la racine, qui configurent et démarrent l'application.

La mise en route tient en trois commandes. La première génère le projet, la dernière lance le serveur.

dotnet new mvc -n LocationWeb
cd LocationWeb
dotnet run

Au démarrage, l'application ecoute sur https://localhost:5001 et affiche une page d'accueil par défaut. Le hot-reload met la page à jour dès que tu modifies et sauves un fichier, sans avoir a tout relancer.

Le pattern MVC

MVC repose sur trois rôles bien séparés. C'est le principe de responsabilité unique (SRP) applique à l'architecture web : chaque partie a une seule raison de changer.

  • Model : les données et la logique métier. C'est la suite directe de ce que tu fais en console (tes classes du domaine, la validation, les calculs).
  • View : le rendu HTML pour le navigateur. Pas de logique métier ici, uniquement la presentation et un peu de logique d'affichage.
  • Controller : l'orchestrateur. Il reçoit la requête HTTP, interroge le model, choisit la view et renvoie la réponse.

Le flux est toujours le même : le navigateur (le client) parle au contrôleur, qui demande les données au model, puis confie le rendu à la view avant de renvoyer la réponse. Le contrôleur coordonne, il ne fait ni le calcul métier ni le rendu.

Cycle d'une requête HTTP

Suivre une requête de bout en bout aide à comprendre ou s'exécute chaque morceau de code. Prenons l'appel GET /Voitures/Detail/5.

  1. Le navigateur envoie la requête HTTP au serveur.
  2. Kestrel et le pipeline de middleware la traitent (authentification, fichiers statiques, etc.).
  3. Le routing la dirige vers VoituresController.Detail(5).
  4. L'action s'exécute et prépare un ViewModel.
  5. La view Razor Detail.cshtml rend le HTML.
  6. La réponse HTTP repart vers le navigateur, qui affiche la page.

Routing : de l'URL vers l'action

Le routing fait le lien entre une URL et une méthode de contrôleur. La convention par défaut decoupe l'URL en trois segments.

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}");

Si un segment est absent, on retombe sur la valeur par défaut, donc Home/Index. Le point d'interrogation sur id indique qu'il est optionnel. Voici comment quelques URLs se traduisent en appels :

RequêteAction appelée
GET /HomeController.Index()
GET /VoituresVoituresController.Index()
GET /Voitures/Detail/5VoituresController.Detail(5)
POST /Voitures/CreateVoituresController.Create(form)
GET /Voitures/Edit/5VoituresController.Edit(5)

L'URL /Voitures/Detail/5 appelle donc Detail(int id) avec id = 5. Le mappage est automatique, tu n'as rien a brancher à la main.

Controllers et actions

On écrit une classe de contrôleur par ressource. Chaque méthode publique est une action, c'est-a-dire un point d'entrée pour une requête.

public class VoituresController : Controller
{
    public IActionResult Index()
    {
        var voitures = _service.Lister();
        return View(voitures);
    }

    public IActionResult Detail(int id)
    {
        var voiture = _service.LirePar(id);
        if (voiture == null) return NotFound();
        return View(voiture);
    }
}

Le type de retour IActionResult permet a une action de renvoyer différentes réponses selon la situation :

  • View() : rend une view Razor.
  • RedirectToAction(...) : redirige vers une autre action.
  • Json(...) : renvoie une charge utile JSON.
  • NotFound() : répond avec un code 404.
  • BadRequest() : répond avec un code 400.

Un contrôleur ne contient ni SQL ni calculs métier. Il orchestre, il ne fait pas le travail lui-même. Cette discipline garde la logique métier dans le model, ou elle reste testable et réutilisable.

Views Razor

Une view Razor mélange du HTML et des instructions C# prefixees par @. La directive @model declare le type de données que la view reçoit.

@model List<Voiture>
<h1>Voitures</h1>
<ul>
@foreach (var v in Model)
{
    <li>
        <a asp-action="Detail" asp-route-id="@v.Id">
            @v.Marque @v.Modele
        </a>
    </li>
}
</ul>

Les éléments de syntaxe a connaître sont peu nombreux :

  • @variable : interpolation d'une valeur dans le HTML.
  • @if (...) { ... } : affichage conditionnel.
  • @foreach (...) { ... } : itération sur une collection.
  • @model T : type du modèle reçu par la view.
  • asp-action, asp-route-* : des tag helpers qui generent les liens et les attributs HTML à partir du routing.

Le fichier _Layout.cshtml contient le gabarit commun a toutes les pages (en-tête, navigation, pied de page). L'appel @RenderBody() indique l'endroit où s'insere le contenu propre à chaque view.

ViewModel : pourquoi ?

Une view doit afficher exactement ce dont elle a besoin, pas plus. Si on lui passe directement une classe du domaine, on l'expose a des champs sensibles ou internes qui n'ont rien à faire dans une page.

// Domaine
class Voiture
{
    public string Marque;
    public decimal TarifJournee;
    public string ConnectionString;
    private int _idInterne;
}

// View couplee au domaine : @model Voiture
// <p>@Model.ConnectionString</p>   // ouille

Exposer ConnectionString dans une page est un problème evident. La solution est de définir un ViewModel dédié, une classe pensee pour l'affichage, et de laisser le contrôleur y projeter les données du domaine.

// ViewModel dedie
class VoitureCardVm
{
    public string Marque { get; set; }
    public string Modele { get; set; }
    public decimal TarifAffiche { get; set; }
}

// Le controleur projette le domaine vers le ViewModel
var vm = new VoitureCardVm
{
    Marque = voiture.Marque,
    Modele = voiture.Modele,
    TarifAffiche = voiture.TarifJournee
};
return View(vm);

Le ViewModel agit comme une frontiere : la view ne dépend que de lui, et le model du domaine reste hors d'atteinte. Tu peux faire évoluer l'un sans casser l'autre.

Forms et model binding

Pour récupérer une saisie utilisateur, on écrit un formulaire HTML dont les champs portent un tag helper asp-for lié a une propriété.

<form asp-action="Create" method="post">
    <input asp-for="Marque" />
    <input asp-for="Modele" />
    <input asp-for="TarifJournee" />
    <button type="submit">Creer</button>
</form>

Cote serveur, l'action reçoit directement un objet typé. Le runtime mappe automatiquement les champs HTML vers les propriétés du paramètre : c'est le model binding.

[HttpPost]
public IActionResult Create(VoitureFormVm form)
{
    if (!ModelState.IsValid) return View(form);

    var voiture = new Voiture(
        form.Marque,
        form.Modele,
        form.TarifJournee);
    _service.Ajouter(voiture);
    return RedirectToAction("Index");
}

Après un enregistrement reussi, on redirige avec RedirectToAction plutôt que de rendre une view. Cela évite qu'un rafraichissement du navigateur ne renvoie le formulaire une seconde fois.

Validation avec les DataAnnotations

La validation se declare sous forme d'attributs sur le ViewModel de formulaire. Chaque règle est lisible directement à côté de la propriété concernee.

public class VoitureFormVm
{
    [Required(ErrorMessage = "Marque requise")]
    [StringLength(50)]
    public string Marque { get; set; }

    [Required]
    [StringLength(50)]
    public string Modele { get; set; }

    [Range(1, 9999, ErrorMessage = "Tarif > 0")]
    public decimal TarifJournee { get; set; }
}

Dans la view, on associe à chaque champ un emplacement pour son message d'erreur grâce au tag helper asp-validation-for.

<form asp-action="Create">
    <input asp-for="Marque" />
    <span asp-validation-for="Marque"></span>
    <input asp-for="TarifJournee" />
    <span asp-validation-for="TarifJournee"></span>
</form>

Dans l'action, le test ModelState.IsValid indique si la saisie respecte toutes les règles. Si la validation échoue, tu re-renvoies la view avec le ViewModel : les messages d'erreur sont déjà attaches aux champs, l'utilisateur voit immediatement ce qu'il faut corriger.

En résumé

ASP.NET Core MVC applique a une application web la séparation des responsabilités que tu connais déjà en C# : le model porte le domaine, la view produit le HTML, le contrôleur orchestre. Le routing relie les URLs aux actions, le model binding transforme un formulaire en objet typé, les ViewModels protegent le domaine, et les DataAnnotations centralisent la validation. Pour voir ces pièces fonctionner ensemble, regarde la demo aspnet-mvc.
