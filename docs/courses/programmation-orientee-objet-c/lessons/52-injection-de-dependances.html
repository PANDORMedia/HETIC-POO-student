Injection de dépendances

slidesDurée : 30 min

Le principe

ASP.NET Core embarque un conteneur de services. Tu enregistres tes services une seule fois, et le framework les injecte là où ils sont nécessaires. Tu n'as plus à construire toi-même tes objets a coups de new : tu declares ce dont tu as besoin, le conteneur s'occupe de le fournir.

Créer un service

Un service repose sur deux éléments : une interface qui représente le contrat, et une classe qui l'implémente. On l'écrit avant de l'enregistrer.

1. L'interface (le contrat)

public interface IVoitureService
{
    List<Voiture> Lister();
    Voiture? Trouver(int id);
    decimal CalculerTarif(Voiture v, int jours);
}

L'interface décrit ce que le service fait, jamais comment. C'est elle que les controllers demanderont.

2. L'implémentation

public class VoitureService : IVoitureService
{
    private readonly IVoitureRepository _repo;

    public VoitureService(IVoitureRepository repo)
    {
        _repo = repo;
    }

    public List<Voiture> Lister() => _repo.All();

    public Voiture? Trouver(int id) =>
        _repo.All().FirstOrDefault(v => v.Id == id);

    public decimal CalculerTarif(Voiture v, int jours) =>
        v.TarifJournalier * jours;
}

La classe dépend de l'abstraction IVoitureRepository, pas d'une implémentation concrète : elle aussi sera injectée. Le principe d'inversion des dépendances se propage en cascade. C'est ce VoitureService qu'on enregistre ensuite dans Program.cs.

Le conteneur de services

L'enregistrement se fait dans Program.cs, au démarrage de l'application.

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllersWithViews();

// Tes services
builder.Services.AddSingleton<IVoitureRepository, VoitureRepositoryJson>();
builder.Services.AddScoped<IVoitureService, VoitureService>();
builder.Services.AddTransient<ITarifCalculator, TarifStandard>();

var app = builder.Build();

La consommation se fait par le constructeur du controller.

public class VoituresController : Controller
{
    private readonly IVoitureService _service;

    public VoituresController(IVoitureService service)
    {
        _service = service;
    }

    // ... actions
}

Tu declares l'interface dans le constructeur. ASP.NET injecte l'implémentation enregistrée.

Les durees de vie

Au moment de l'enregistrement, tu choisis combien de temps une instance doit vivre. Trois options existent.

Duree de viePortéeQuand l'utiliser
SingletonUne seule instance pour toute l'application, créée au premier usage et conservee jusqu'à l'arret.Caches, repositories en mémoire, services sans état globaux. La sécurité des threads est obligatoire si l'état est mutable.
ScopedUne instance par requête HTTP, partagée entre les services d'une même requête.DbContext, unit of work, contexte utilisateur.
TransientUne nouvelle instance à chaque injection, a vie courte et sans état conserve.Services sans état légers, calculs simples.

En cas de doute, commence par Scoped. C'est le choix par défaut le plus sur pour la plupart des cas.

Résolution en chaine

Le runtime construit toute la chaine de dépendances automatiquement à partir des enregistrements de Program.cs. Pour une requête GET /Voitures, l'enchaînement est le suivant :

  1. Besoin : VoituresController.
  2. Son constructeur demande IVoitureService ; le conteneur fournit VoitureService.
  3. Le constructeur de ce dernier demande IVoitureRepository ; le conteneur fournit VoitureRepositoryJson.
  4. L'injection remonte en cascade : VoituresController est instancie et prêt à servir.

Tu n'ecris aucun new pour assembler cette chaine. Tu decris les contrats et leurs implémentations, le conteneur se charge du reste.
