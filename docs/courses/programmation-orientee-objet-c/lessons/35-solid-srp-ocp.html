SOLID : SRP & OCP

readingDurée : 20 min

SOLID : cinq principes pour un code durable

SOLID regroupe cinq principes de conception orientée objet. Leur objectif commun est simple : écrire du code qui ne devient pas un cauchemar a maintenir six mois plus tard. Comme le résumé Robert C. Martin, "un code qui doit changer chaque semaine est un code mal designé". Quand chaque modification en casse trois autres, le problème n'est pas le volume de code, mais la façon dont les responsabilités y sont réparties.

Voici les cinq principes en une phrase chacun :

  • S - Single Responsibility : une classe, une seule raison de changer. Pas dix.
  • O - Open/Closed : ouvert à l'extension, fermé à la modification.
  • L - Liskov Substitution : une classe fille peut remplacer son parent sans surprise.
  • I - Interface Segregation : plusieurs petites interfaces plutôt qu'une grosse.
  • D - Dependency Inversion : dépendre d'abstractions, pas d'implémentations.

Cette leçon detaille les deux premiers, S et O, qui forment la base sur laquelle reposent les trois autres.

SRP : une seule responsabilité

Le principe de responsabilité unique dit qu'une classe doit avoir une seule raison de changer. Une "raison de changer" correspond a un acteur ou a une preoccupation : une règle métier, un schéma de base de données, un protocole d'envoi, une mise en page. Si plusieurs de ces preoccupations cohabitent dans la même classe, chacune devient un motif distinct de modification, et toute evolution de l'une risque de perturber les autres.

Voici une classe qui viole le principe. Elle fait quatre choses sans rapport entre elles :

class Facture
{
    public void Calculer() { ... }
    public void SauverEnBase() { ... }
    public void EnvoyerParMail() { ... }
    public string GenererPdf() { ... }
}

Cette classe a quatre raisons de changer : la règle métier de calcul, le schéma de la base de données, la configuration SMTP de l'envoi, et la mise en page du PDF. Un changement de serveur mail n'a aucune raison d'affecter le code qui calcule un montant, et pourtant ils sont melanges.

La version correcte séparé chaque responsabilité dans sa propre classe :

class Facture
{
    public void Calculer() { ... }
}

class FactureRepository
{
    public void Sauver(...) { ... }
}

class FactureMailer
{
    public void Envoyer(...) { ... }
}

class FacturePdfGenerator
{
    public string Generer(...) { ... }
}

Chaque classe porte une seule responsabilité et evolue indépendamment des autres. Modifier le format du PDF ne touche plus jamais au calcul du montant ni à la persistance.

Détecter une violation de SRP

Trois tests rapides aident a repérer une classe qui en fait trop :

  • Le test du "ET" : si la description de la classe contient un "et", c'est probablement deux responsabilités. "Elle valide et sauvegarde" signale déjà deux preoccupations.
  • Le test des acteurs : combien de personnes différentes peuvent demander un changement sur cette classe ? Le métier pour les règles de calcul, l'équipe infrastructure pour la base, l'équipe communication pour les mails. Si la réponse dépassé une personne, il faut scinder.
  • Le test du nom : si tu peines a nommer la classe sans recourir a "Manager", "Helper" ou "Util", c'est souvent qu'elle fait trop de choses. Un nom précis traduit une responsabilité précise.

OCP : ouvert à l'extension, fermé à la modification

Le principe ouvert/fermé demande de pouvoir ajouter du comportement sans toucher au code qui fonctionne déjà. Autrement dit, une nouvelle fonctionnalite devrait se traduire par du code ajoute, pas par du code existant réécrit. Le code qui marche reste figé ; les points d'extension prevus accueillent les nouveautes.

Voici une violation typique. Chaque nouveau tarif oblige a rouvrir la même méthode :

class CalculTarif
{
    public decimal Calculer(string type)
    {
        if (type == "standard") return ...;
        else if (type == "weekend") return ...;
        else if (type == "promo") return ...;
        // Ajouter un tarif = modifier cette methode
    }
}

Chaque ajout de tarif modifie une méthode existante et déjà testée, avec le risque de casser les cas précédents. La chaine de if/else grandit sans fin.

La version qui respecte OCP introduit une abstraction. Chaque tarif devient une classe qui implémente une interface commune :

interface ITarif
{
    decimal Calculer(...);
}

class TarifStandard : ITarif { ... }
class TarifWeekend : ITarif { ... }
class TarifPromo : ITarif { ... }

// Ajouter un tarif = creer une classe.
// Aucune ligne existante ne change.

Pour ajouter un nouveau tarif, il suffit de créer une nouvelle classe qui implémente ITarif. Aucune ligne du code existant ne change, donc rien de ce qui marchait déjà ne peut casser. L'ensemble est fermé à la modification mais ouvert à l'extension.

Une comparaison : le système de plugins

Un éditeur comme VS Code illustre bien OCP. Pour ajouter le support du C#, on n'a pas modifie le code source de l'éditeur : on a installe une extension qui se branche sur un contrat d'extension figé. Le C# Dev Kit, Prettier, GitLens, un plugin Vim ou l'extension de demain se connectent tous au même point d'extension stable.

L'éditeur reste fermé à la modification, tandis que son système d'extension reste ouvert. C'est exactement ce que vise OCP : un noyau stable, et des points d'extension prevus pour accueillir ce qui n'existe pas encore.

À retenir

SRP et OCP se complètent. SRP repartit les responsabilités pour qu'une classe n'ait qu'une raison de changer ; OCP organise le code pour qu'on l'etende sans le réécrire. Ensemble, ils reduisent les effets de bord : une modification reste locale, et une nouveauté s'ajoute sans toucher à l'existant. C'est la base d'un code qui supporte le changement au lieu de le craindre.
