Models & Controllers OOP

slidesDurée : 30 min

Le pattern MVC

MVC repose sur trois rôles et une séparation claire des responsabilités. C'est le principe de responsabilité unique (SRP) applique à l'architecture web. Chaque partie a un travail précis, et une seule raison de changer.

  • Model : les données et la logique métier. C'est la suite directe de ce que tu fais en console, avec tes classes du domaine, la validation et les calculs. C'est la cuisine.
  • View : le rendu HTML pour le navigateur. Pas de logique métier ici, juste la presentation et un peu de logique d'affichage. C'est la salle.
  • Controller : l'orchestrateur. Il reçoit la requête HTTP, demande au model, choisit la view et renvoie la réponse. C'est le serveur.

Le client (le navigateur) parle au serveur (le contrôleur), qui parle à la cuisine (le model), qui revient via la salle (la view).

Controllers et actions

Une classe par ressource. Chaque méthode publique qui retourne un IActionResult est une action.

public class VoituresController : Controller
{
    public IActionResult Index()
    {
        var voitures = _service.Lister();
        return View(voitures);
    }

    public IActionResult Detail(int id)
    {
        var voiture = _service.LirePar(id);
        if (voiture == null)
            return NotFound();
        return View(voiture);
    }
}

Les types de retour courants :

  • View() : rend une vue Razor.
  • RedirectToAction(...) : redirige vers une autre action.
  • Json(...) : renvoie une charge utile JSON.
  • NotFound() : réponse 404.
  • BadRequest() : réponse 400.

Pas de SQL ni de calculs métier dans le contrôleur. Il orchestre, il ne fait pas le travail lui-même.

Views Razor

Une vue declare le type de modèle qu'elle attend, puis mélange du HTML et des instructions Razor pour produire la page.

@model List<Voiture>
<h1>Voitures</h1>
<ul>
@foreach (var v in Model)
{
    <li>
        <a asp-action="Detail" asp-route-id="@v.Id">
            @v.Marque @v.Modele
        </a>
    </li>
}
</ul>

Razor essentiel :

  • @variable : interpolation d'une valeur.
  • @if (...) { ... } : bloc conditionnel.
  • @foreach (...) { ... } : itération sur une collection.
  • @model T : type du modèle reçu par la vue.
  • asp-action, asp-route-* : tag helpers pour générer les liens.

Le fichier _Layout.cshtml contient le template commun a toutes les pages. L'appel @RenderBody() indique l'endroit où vient se placer le contenu de chaque vue.

ViewModel : pourquoi ?

Une vue affiche ce dont elle a besoin, pas plus. En lui passant directement une classe du domaine, on expose des propriétés internes ou sensibles dont la presentation n'a que faire. Le ViewModel évite ce couplage : le model du domaine reste hors d'atteinte de la vue.

Vue couplée au domaine, a éviter :

// Domaine
class Voiture
{
    public string Marque;
    public decimal TarifJournee;
    public string ConnectionString;
    private int _idInterne;
}

// Vue : @model Voiture
// <p>@Model.ConnectionString</p>  // ouille, on expose un detail interne

Vue avec un ViewModel dédié :

// ViewModel dedie a l'affichage
class VoitureCardVm
{
    public string Marque { get; set; }
    public string Modele { get; set; }
    public decimal TarifAffiche { get; set; }
}

// Le controleur projette le domaine vers le ViewModel
var vm = new VoitureCardVm
{
    Marque = voiture.Marque,
    Modele = voiture.Modele,
    TarifAffiche = voiture.TarifJournee
};
return View(vm);

Le contrôleur reste l'orchestrateur : il lit le model, construit le ViewModel adapté à la vue, et ne laisse fuiter aucun detail interne du domaine vers la presentation.
