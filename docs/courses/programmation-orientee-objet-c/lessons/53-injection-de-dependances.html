Injection de dépendances

readingDurée : 20 min

Le conteneur de services d'ASP.NET Core

ASP.NET Core intégré un conteneur de services. L'idée est simple : au lieu de créer toi-même les objets dont tes classes ont besoin (avec new), tu enregistres tes services au démarrage de l'application et tu laisses le framework les fournir là où ils sont reclames. C'est l'application directe du principe d'inversion des dépendances (DIP) : une classe ne fabrique pas ses dépendances, elle les reçoit.

Ce mécanisme s'appelle l'injection de dépendances. Tu declares un besoin (une interface) dans le constructeur d'une classe, et le conteneur se charge de fournir l'implémentation concrète que tu as enregistrée. Le code devient plus simple à tester et à faire évoluer, parce que chaque classe dépend d'un contrat, jamais d'une classe concrète.

Créer un service

Un service se compose de deux parties : une interface qui sert de contrat, et une classe qui l'implémente. On écrit toujours les deux avant de pouvoir enregistrer le service dans le conteneur.

1. L'interface, le contrat

L'interface décrit ce que le service fait, jamais comment il le fait. C'est elle que les contrôleurs demanderont, sans rien savoir de l'implémentation réelle.

public interface IVoitureService
{
    List<Voiture> Lister();
    Voiture? Trouver(int id);
    decimal CalculerTarif(Voiture v, int jours);
}

2. L'implémentation

La classe fournit le comportement réel. Remarque qu'elle dépend elle-même d'une abstraction, IVoitureRepository, et non d'une implémentation concrète : ce repository sera lui aussi injecte. Le DIP se propage donc en cascade, de couche en couche.

public class VoitureService : IVoitureService
{
    private readonly IVoitureRepository _repo;

    public VoitureService(IVoitureRepository repo)
    {
        _repo = repo;
    }

    public List<Voiture> Lister() => _repo.All();

    public Voiture? Trouver(int id) =>
        _repo.All().FirstOrDefault(v => v.Id == id);

    public decimal CalculerTarif(Voiture v, int jours) =>
        v.TarifJournalier * jours;
}

C'est ce VoitureService qu'on enregistre ensuite dans Program.cs.

Enregistrer et consommer un service

L'enregistrement se fait au démarrage, dans Program.cs, sur l'objet builder.Services. Chaque appel associe une interface a son implémentation, en precisant la duree de vie (le lifetime) souhaitee.

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllersWithViews();

// Tes services
builder.Services.AddSingleton<IVoitureRepository, VoitureRepositoryJson>();
builder.Services.AddScoped<IVoitureService, VoitureService>();
builder.Services.AddTransient<ITarifCalculator, TarifStandard>();

var app = builder.Build();

Cote consommation, le contrôleur declare simplement l'interface dont il a besoin dans son constructeur. ASP.NET injecte l'implémentation enregistrée au moment de créer le contrôleur.

public class VoituresController : Controller
{
    private readonly IVoitureService _service;

    public VoituresController(IVoitureService service)
    {
        _service = service;
    }

    // ... actions
}

Le contrôleur ne fait jamais new VoitureService(...). Il declare son besoin, le conteneur s'occupe du reste.

Les durees de vie : Singleton, Scoped, Transient

Quand tu enregistres un service, tu choisis combien de temps son instance doit vivre. Trois durees de vie existent, chacune adaptée a un usage différent.

Singleton

Une seule instance pour toute l'application. Elle est créée au premier usage et vit jusqu'à l'arret du serveur. C'est le bon choix pour les caches, les repositories en mémoire ou les services sans état partagés globalement. Attention : si l'instance contient un état mutable, tu dois garantir sa sécurité face aux accès concurrents (thread safety).

Scoped

Une instance par requête HTTP. Elle est recréée à chaque requête et partagée entre tous les services qui interviennent dans cette même requête. C'est la duree de vie typique d'un DbContext, d'un unit of work ou d'un contexte utilisateur.

Transient

Une nouvelle instance à chaque injection. Sa vie est courte et elle ne conserve aucun état. On la réserve aux services légers et sans état, comme de simples calculs.

En cas de doute, commence par Scoped : c'est le défaut le plus sur pour la plupart des cas.

LifetimePortée de l'instanceCas d'usage
SingletonToute l'applicationCaches, repositories en mémoire, services stateless globaux
ScopedUne requête HTTPDbContext, unit of work, contexte utilisateur
TransientUne injectionServices légers, calculs simples

La résolution en chaine

Le plus intéressant, c'est que tu n'as jamais a assembler toi-même la chaine d'objets. À partir des enregistrements de Program.cs, le runtime construit automatiquement toute la chaine de dépendances pour répondre a une requête.

Prenons une requête GET /Voitures. Le runtime suit la chaine suivante :

  1. Il a besoin d'un VoituresController.
  2. Le constructeur du contrôleur demande un IVoitureService : le conteneur fournit un VoitureService.
  3. Le constructeur de VoitureService demande un IVoitureRepository : le conteneur fournit un VoitureRepositoryJson.
  4. L'injection se fait en cascade, de la dépendance la plus profonde vers la plus haute.
  5. Le VoituresController est instancie, complètement cable et prêt à servir.

Chaque classe se contente de déclarer ses besoins via son constructeur. Le conteneur résout l'arbre complet des dépendances, ce qui te laisse des classes isolées, faciles à tester et a remplacer. Tu peux voir ce decoupage à l'oeuvre dans la demo aspnet-mvc.
