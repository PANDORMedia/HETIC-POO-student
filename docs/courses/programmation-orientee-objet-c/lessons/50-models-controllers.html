Models & Controllers

readingDurée : 20 min

Le contrôleur orchestre la requête

Dans une application MVC, le contrôleur est le point d'entrée d'une requête HTTP. On lui confie une seule famille de responsabilités : recevoir l'appel, demander le travail au service métier, puis choisir la réponse a renvoyer. La convention est d'avoir une classe par ressource, et chaque méthode publique du contrôleur correspond a une action accessible par une URL.

public class VoituresController : Controller
{
    public IActionResult Index()
    {
        var voitures = _service.Lister();
        return View(voitures);
    }

    public IActionResult Detail(int id)
    {
        var voiture = _service.LirePar(id);
        if (voiture == null) return NotFound();
        return View(voiture);
    }
}

Le point à retenir : pas de SQL ni de calcul métier dans le contrôleur. Il orchestre, il ne fait pas le travail lui-même. Toute la logique appartient au service, que le contrôleur appelle à travers une référence (_service) recue par injection de dépendances.

Les types de retour d'une action

Une action retourne un IActionResult, ce qui laisse le choix de la forme de la réponse selon la situation.

RetourEffet
View(modele)rend une vue Razor
RedirectToAction(...)redirige vers une autre action
Json(...)renvoie un payload JSON
NotFound()répond 404
BadRequest()répond 400

Dans l'action Detail ci-dessus, on illustre ce choix : si la voiture demandée n'existe pas, on renvoie NotFound() plutôt que de tenter d'afficher une vue avec un modèle vide.

Les vues Razor

Une vue Razor est un gabarit HTML auquel on ajoute des instructions C# pour injecter des données. La directive @model en tête declare le type de modèle que la vue reçoit, et la propriété Model donne accès à l'instance transmise par le contrôleur.

@model List<Voiture>
<h1>Voitures</h1>
<ul>
@foreach (var v in Model)
{
    <li>
        <a asp-action="Detail" asp-route-id="@v.Id">
            @v.Marque @v.Modele
        </a>
    </li>
}
</ul>

La syntaxe Razor reste limitee a quelques constructions :

  • @variable : interpolation d'une valeur
  • @if (...) { ... } : conditionnel
  • @foreach (...) { ... } : itération
  • @model T : type du modèle reçu
  • asp-action, asp-route-* : tag helpers qui generent les URLs et les liens

Le fichier _Layout.cshtml contient le gabarit commun a toutes les pages (entête, navigation, pied de page). La directive @RenderBody() indique l'emplacement ou le contenu propre à chaque vue vient se loger.

Le ViewModel : afficher juste ce qu'il faut

Une vue affiche ce dont elle a besoin, pas plus. Le modèle du domaine, lui, doit rester hors d'atteinte de la couche de presentation. Quand on couplé directement une vue a une classe du domaine, on expose des données qui n'ont rien à faire dans une page.

// Domaine
class Voiture
{
    public string Marque;
    public decimal TarifJournee;
    public string ConnectionString;
    private int _idInterne;
}

// Vue : @model Voiture
// <p>@Model.ConnectionString</p>  // a eviter

Afficher une chaine de connexion dans une page est evidemment un problème. La solution est de définir un ViewModel dédié, une classe qui ne contient que les propriétés utiles à l'affichage. Le contrôleur projette le modèle du domaine vers ce ViewModel avant de le passer à la vue.

// ViewModel dedie
class VoitureCardVm
{
    public string Marque { get; set; }
    public string Modele { get; set; }
    public decimal TarifAffiche { get; set; }
}

// Le controleur projette
var vm = new VoitureCardVm
{
    Marque = voiture.Marque,
    Modele = voiture.Modele,
    TarifAffiche = voiture.TarifJournee
};
return View(vm);

Ce découplage a plusieurs interets : la vue ne dépend plus de la structure interne du domaine, on ne risque plus de divulguer des données sensibles, et on peut faire évoluer le modèle métier sans casser les pages.

Les formulaires et le ModelBinding

Pour créer ou modifier une ressource, on envoie un formulaire HTML. Le tag helper asp-for relie chaque champ a une propriété du modèle, ce qui garantit que les noms cote serveur et cote client restent coherents.

<form asp-action="Create" method="post">
    <input asp-for="Marque" />
    <input asp-for="Modele" />
    <input asp-for="TarifJournee" />
    <button type="submit">Creer</button>
</form>

Cote serveur, l'action de reception reçoit directement un objet rempli. C'est le ModelBinding : le runtime mappe automatiquement les champs HTML vers les propriétés du paramètre, en se basant sur leurs noms.

[HttpPost]
public IActionResult Create(VoitureFormVm form)
{
    if (!ModelState.IsValid) return View(form);

    var voiture = new Voiture(
        form.Marque,
        form.Modele,
        form.TarifJournee);

    _service.Ajouter(voiture);
    return RedirectToAction("Index");
}

L'attribut [HttpPost] réserve cette action aux soumissions de formulaire. Après l'ajout reussi, on redirige vers Index plutôt que de rendre une vue : cela évite qu'un rafraichissement de page renvoie le formulaire une seconde fois.

La validation avec les DataAnnotations

Les règles de validation se declarent par des attributs poses sur les propriétés du ViewModel. Elles définissent ce qu'est une saisie acceptable, au plus pres des données concernees.

public class VoitureFormVm
{
    [Required(ErrorMessage = "Marque requise")]
    [StringLength(50)]
    public string Marque { get; set; }

    [Required]
    [StringLength(50)]
    public string Modele { get; set; }

    [Range(1, 9999, ErrorMessage = "Tarif > 0")]
    public decimal TarifJournee { get; set; }
}

Dans la vue, le tag helper asp-validation-for réserve l'emplacement ou s'affichera le message d'erreur associé à un champ.

<form asp-action="Create">
    <input asp-for="Marque" />
    <span asp-validation-for="Marque"></span>
    <input asp-for="TarifJournee" />
    <span asp-validation-for="TarifJournee"></span>
</form>

Dans l'action, on teste ModelState.IsValid. Si la validation échoue, on re-renvoie la vue avec le ViewModel : les erreurs y sont déjà attachées et s'affichent automatiquement à côté des champs concernes. On ne traite la requête que lorsque l'état du modèle est valide.

Mettre tout en pratique

Ces éléments - contrôleur, vue, ViewModel, ModelBinding et validation - forment le coeur d'une application web MVC. Pour voir l'ensemble fonctionner sur un exemple complet, parcours la demo aspnet-mvc, dont le code se trouve dans demos/aspnet-mvc.
