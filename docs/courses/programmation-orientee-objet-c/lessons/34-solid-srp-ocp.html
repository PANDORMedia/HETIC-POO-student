SOLID : SRP & OCP

slidesDurée : 30 min

SOLID : cinq principes de conception

SOLID regroupe cinq principes pour écrire du code qui ne devient pas un cauchemar dans six mois. L'idée de fond, resumee par Robert C. Martin : un code qui doit changer chaque semaine est un code mal conçu. Ces principes guident la façon dont on decoupe les responsabilités et dont on organise les dépendances entre classes.

Les cinq principes en un coup d'oeil

  • S - Single Responsibility : une classe, une seule raison de changer. Pas dix.
  • O - Open/Closed : ouvert à l'extension, fermé à la modification.
  • L - Liskov Substitution : une classe fille peut remplacer son parent sans surprise.
  • I - Interface Segregation : plusieurs petites interfaces plutôt qu'une grosse.
  • D - Dependency Inversion : dépendre d'abstractions, pas d'implémentations.

Cette page detaille les deux premiers : SRP et OCP.

SRP : une seule responsabilité

Une classe doit avoir une seule raison de changer. Quand une même classe mélange plusieurs preoccupations, chaque evolution de l'une risque de casser les autres.

A éviter

class Facture
{
    public void Calculer() { ... }
    public void SauverEnBase() { ... }
    public void EnvoyerParMail() { ... }
    public string GenererPdf() { ... }
}

Cette classe a quatre raisons de changer : la règle métier du calcul, le schéma de la base de données, la configuration SMTP et la mise en page du PDF. Quatre preoccupations independantes reunies au même endroit.

Une responsabilité par classe

class Facture
{
    public void Calculer() { ... }
}

class FactureRepository
{
    public void Sauver(...) { ... }
}

class FactureMailer
{
    public void Envoyer(...) { ... }
}

class FacturePdfGenerator
{
    public string Generer(...) { ... }
}

Chaque classe porte une seule responsabilité et evolue indépendamment des autres.

Détecter une violation de SRP

  • Le test du ET : si la description de la classe contient un "et", il y a probablement deux responsabilités. Par exemple "elle valide et sauve".
  • Le test des demandeurs : combien de personnes différentes peuvent demander un changement sur cette classe ? Si plus d'une, il faut la scinder.
  • Le test du nom : si on peine a nommer la classe sans recourir a "Manager", "Helper" ou "Util", c'est souvent qu'elle fait trop de choses.

OCP : ouvert à l'extension, fermé à la modification

On doit pouvoir ajouter du comportement sans toucher au code qui fonctionne déjà. Le code existant reste stable, les nouveaux cas s'ajoutent à côté.

A éviter

class CalculTarif
{
    public decimal Calculer(string type)
    {
        if (type == "standard") return ...;
        else if (type == "weekend") return ...;
        else if (type == "promo") return ...;
        // Ajouter un tarif = modifier cette methode
    }
}

Chaque nouveau tarif oblige a rouvrir cette méthode et a y ajouter une branche, au risque de casser les cas existants.

OCP respecte

interface ITarif
{
    decimal Calculer(...);
}

class TarifStandard : ITarif { ... }
class TarifWeekend : ITarif { ... }
class TarifPromo : ITarif { ... }

// Ajouter un tarif = creer une classe.
// Aucune ligne existante ne change.

Ajouter un tarif revient a créer une nouvelle classe qui implémente l'interface. Aucune ligne du code en place n'est modifiée.

L'analogie des extensions

VS Code n'est pas modifie pour ajouter le support du C# : l'extension se branche sur un contrat d'extension figé. Des extensions comme C# Dev Kit, Prettier, GitLens ou Vim viennent se connecter sans toucher au coeur de l'éditeur, et l'extension de demain fera de même. L'éditeur reste fermé à la modification, mais son système d'extension est ouvert. C'est exactement l'esprit d'OCP.
