SOLID : LSP, ISP & DIP

readingDurée : 20 min

Après SRP et OCP, les trois dernières lettres de SOLID complètent le tableau : le principe de substitution de Liskov (LSP), la segregation des interfaces (ISP) et l'inversion des dépendances (DIP). Ces trois principes partagent une même idée : le code qui consomme une abstraction ne doit jamais avoir de mauvaise surprise, et il ne doit dépendre que de ce dont il a vraiment besoin.

LSP : substituer sans surprise

Le principe de substitution de Liskov demande qu'une instance de classe fille puisse remplacer une instance de classe parent sans casser le code qui l'appelle. Si une méthode accepte un Rectangle, elle doit fonctionner aussi bien avec n'importe quel sous-type de Rectangle, sans avoir a connaître le type concret.

L'exemple classique de violation est celui du carre qui hérite du rectangle. Mathematiquement, un carre est un rectangle particulier, alors on est tente d'écrire un héritage.

class Rectangle
{
    public virtual int Largeur { get; set; }
    public virtual int Hauteur { get; set; }
}

class Carre : Rectangle
{
    public override int Largeur
    {
        set { base.Largeur = value; base.Hauteur = value; }
    }
    // ... idem pour Hauteur : modifier l'un modifie l'autre
}

Le problème apparait des qu'un appelant manipule la référence comme un simple Rectangle.

void Test(Rectangle r)
{
    r.Largeur = 4;
    r.Hauteur = 5;
    Console.WriteLine(r.Largeur * r.Hauteur);
    // Attendu : 20
    // Recoit un Carre : 25
}

Le code qui dépend de Rectangle casse silencieusement quand on lui passe un Carre. Rien ne plante, aucune exception n'est levée, mais le résultat est faux. C'est le pire type de bug : il se cache derrière un contrat que la classe fille a viole sans le dire. Le carre a change le comportement attendu d'un setter, et l'appelant n'a aucun moyen de le savoir.

La bonne abstraction

Hériter pour économiser deux champs ne vaut pas une violation de LSP. La question a se poser n'est pas "est-ce qu'un carre est un rectangle dans la vraie vie", mais "est-ce qu'un carre se comporte comme un rectangle partout où un rectangle est attendu". La réponse est non, donc l'héritage est le mauvais outil.

Une interface partagée fait mieux le travail. On définit un contrat commun, et chaque forme l'implémente a sa façon, sans relation parent-enfant entre elles.

interface IForme
{
    int CalculerAire();
}

class Rectangle : IForme
{
    public int Largeur { get; set; }
    public int Hauteur { get; set; }
    public int CalculerAire() => Largeur * Hauteur;
}

class Carre : IForme
{
    public int Cote { get; set; }
    public int CalculerAire() => Cote * Cote;
}

Il n'y a plus d'héritage entre Carre et Rectangle. L'interface suffit pour le polymorphisme : un appelant qui reçoit un IForme peut appeler CalculerAire() sans jamais se retrouver piège par un setter qui modifie une autre propriété dans son dos.

ISP : interfaces fines

La segregation des interfaces énoncé qu'il vaut mieux plusieurs petites interfaces ciblees qu'une seule grosse interface fourre-tout. Personne ne devrait être force d'implémenter des méthodes qu'il n'utilise pas.

Prenons une interface qui rassemble toutes les fonctions d'un appareil de bureau.

interface IMachine
{
    void Imprimer(...);
    void Scanner(...);
    void Faxer(...);
    void Photocopier(...);
}

class ImprimanteSimple : IMachine
{
    public void Imprimer(...) { ... }
    public void Scanner(...) { throw new NotImplementedException(); }
    public void Faxer(...) { throw new NotImplementedException(); }
    public void Photocopier(...) { throw new NotImplementedException(); }
}

Une imprimante qui ne sait qu'imprimer se retrouve obligee de déclarer trois méthodes vides ou qui lancent une exception. Ces NotImplementedException sont un signal clair : l'interface est trop large pour cette classe. Pire, un appelant qui reçoit un IMachine croit pouvoir appeler Scanner et découvre le problème seulement à l'exécution.

La solution consiste à découper l'interface en contrats fins, chacun centre sur une responsabilité.

interface IImprime { void Imprimer(...); }
interface IScan    { void Scanner(...); }
interface IFax     { void Faxer(...); }

class ImprimanteSimple : IImprime { ... }

class MultiFonctions : IImprime, IScan, IFax { ... }

Chaque classe implémente exactement les contrats qu'elle remplit. L'imprimante simple ne porte que IImprime, la multifonction combine les trois. Un appelant qui n'a besoin que d'imprimer demande un IImprime et ne dépend de rien d'autre. Plus aucune méthode vide, plus aucune surprise à l'exécution.

DIP : dépendre des abstractions

L'inversion des dépendances énoncé deux règles complémentaires : les modules de haut niveau ne doivent pas dépendre des modules de bas niveau, et les deux doivent dépendre d'abstractions. Le but est de detacher la logique métier des détails techniques comme la base de données.

Voici un couplage direct, ou le service crée lui-même son dépôt concret.

class CommandeService
{
    private SqlServerRepository _repo = new SqlServerRepository();

    public void Valider(Commande c)
    {
        _repo.Sauver(c);
    }
}

Ce code est rigide. Il est impossible de tester CommandeService sans un vrai SQL Server, et impossible de changer de base de données sans toucher au service lui-même. La logique métier est soudee a un detail d'infrastructure.

On inverse la dépendance en introduisant une abstraction et en injectant l'implémentation par le constructeur.

interface IRepository<T>
{
    void Sauver(T entity);
}

class CommandeService
{
    private IRepository<Commande> _repo;

    public CommandeService(IRepository<Commande> repo)
    {
        _repo = repo;
    }
}

Le service dépend désormais d'une abstraction, IRepository<Commande>, et non d'une classe concrète. Tu lui injectes l'implémentation de ton choix : un SqlServerRepository en production, un faux dépôt en mémoire pour les tests.

L'inversion des flèches

Le nom du principe vient du sens des flèches de dépendance. Avant l'inversion, le haut niveau pointe vers le bas niveau :

  • CommandeService (haut niveau) dépend de SqlServerRepository (bas niveau).
  • Le haut connait le bas. Le couplage est rigide.

Après l'inversion, les deux pointent vers l'abstraction placee au milieu :

  • CommandeService (haut niveau) dépend de IRepository (abstraction).
  • SqlServerRepository (bas niveau) implémente IRepository.

Les deux modules dépendent de l'abstraction, et c'est le module de bas niveau qui s'y conforme. La fleche entre le service et le dépôt concret a été inversée : le detail technique se branche sur le contrat, au lieu que la logique métier ne se branche sur le detail.

À retenir

  • LSP : une classe fille doit pouvoir remplacer son parent sans changer le comportement attendu. Quand l'héritage casse ce contrat, préfère une interface partagée.
  • ISP : decoupe les grosses interfaces en contrats fins, pour qu'aucune classe n'implémente de méthodes inutiles.
  • DIP : fais dépendre la logique métier d'abstractions, puis injecte les implémentations concrètes. Le métier reste testable et indépendant de l'infrastructure.
